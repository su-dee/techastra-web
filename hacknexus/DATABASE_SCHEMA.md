# HACK_NEXUS PostgreSQL schema

The executable schema is in [`server/schema.sql`](server/schema.sql). Run `npm run dev:local` to initialize a persistent local PostgreSQL database and start the app. For an existing PostgreSQL server, set `DATABASE_URL` and run `npm run db:migrate`.

## Relationships

```text
users (1) ──── (many) sessions
  │
  └────────── (0 or 1) registrations ──── (0 or squad_size) registration_members
```

One user is the lead operator for one squad. A squad has 2–4 participants, whose details are stored in `registration_members`. Deleting an account cascades to its sessions, registration, and members.

## users

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | UUID | Primary key; generated by the server |
| `username` | VARCHAR(30) | Unique, required; normalized to lowercase; 3–30 letters, digits, underscores |
| `password_hash` | TEXT | Required; salted scrypt hash of the password |
| `password_kind` | VARCHAR(10) | `chosen` (default), `mobile` (account created when the mobile number was the password), or `temporary` (issued by an organizer); added by `006_passwords.sql` |
| `created_at` | TIMESTAMPTZ | Required; defaults to `NOW()` |

The user signs in with a **username and password**. New passwords must be 8–128 characters, must not be a phone number, and must not equal the username.

Accounts created before chosen passwords existed have `password_kind = mobile`: their password is the mobile number, compared as digits only (formatting characters are removed; the 10–15 digits must match those used at signup). After signing in with it, and likewise with an organizer-issued temporary password, the API reports `mustSetPassword: true` and the site asks the user to choose a password before continuing. Setting a password signs out the account's other sessions.

Hash format: `scrypt:<random 16-byte salt in hex>:<64-byte derived key in hex>`. Parameters: N=32768, r=8, p=1. Password verification uses a timing-safe comparison. Each account has its own random salt.

**Limitations:** there is no self-service password reset; organizers issue temporary passwords from Admin → Accounts. Email addresses and phone numbers are not verified.

## sessions

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `token_hash` | CHAR(64) | Primary key; SHA-256 digest of a cryptographically random 32-byte token |
| `user_id` | UUID | Required foreign key → `users.id`, cascade on delete |
| `created_at` | TIMESTAMPTZ | Required; defaults to `NOW()` |
| `expires_at` | TIMESTAMPTZ | Required; seven days from session creation |

Indexes: `sessions_user_id_idx` and `sessions_expires_at_idx`. The raw token exists only in the browser's `hn_session` HTTP-only cookie. The cookie uses `SameSite=Strict`, `Path=/`, and `Secure` in production. Login rotates the current session, logout deletes it, and expired sessions are rejected. Expired rows are cleaned when a session is created. Authentication and registration API responses use `Cache-Control: no-store`.

## registrations

| Column | Type | Constraints / purpose |
| --- | --- | --- |
| `id` | UUID | Primary key; registration reference |
| `user_id` | UUID | Unique, required foreign key → `users.id`, cascade on delete |
| `team_name` | VARCHAR(30) | Required, 3–30 characters; case- and whitespace-insensitive unique indexes |
| `lead_email` | VARCHAR(254) | Required; validated by the API |
| `domain` | VARCHAR(10) | Optional (`NULL` when undecided); otherwise `HN-AI`, `HN-CS`, `HN-FT`, or `HN-X` |
| `squad_size` | SMALLINT | Required; 2–4 |
| `problem_id` | VARCHAR(20) | Optional; must be one of the 15 published challenges and match the domain |
| `abstract` | TEXT | Required; defaults to empty string; at most 3,000 characters |
| `conduct_accepted` | BOOLEAN | Required and must be true |
| `created_at` | TIMESTAMPTZ | Required; defaults to `NOW()` |

Unique indexes: `registrations_team_name_idx` on `LOWER(team_name)` and `registrations_team_identity_idx` on the lowercased, trimmed name with repeated whitespace collapsed. The API normalizes whitespace before saving. These database indexes reject concurrent or cross-account duplicate submissions; each account is also limited to one squad. This identifies teams by name/account, not by member identity, since individual member details are not collected. If no domain or challenge is selected, both fields remain NULL. Selecting a challenge supplies its domain automatically; conflicting explicit selections are rejected. Domain/challenge consistency, squad size, and conduct acceptance are enforced both by the API and database constraints. No email or Discord notification is sent by this application.

## Admin tables and columns

`server/migrations/003_admin.sql` adds these. It is idempotent and applied by `npm run db:migrate`, `npm run dev:local`, and `npm run admin:create`.

| Table / column | Purpose |
| --- | --- |
| `admins.user_id` | Primary key and foreign key → `users.id`, cascade on delete |
| `admins.password_hash` | Salted scrypt hash of the separate admin password (12+ characters) |
| `sessions.is_admin` | TRUE for admin sessions (8 hours, `hn_admin` cookie, path `/api/admin`). Participant routes reject admin sessions, and admin routes reject participant sessions. |
| `registrations.status` | `pending` (default), `approved`, `waitlisted`, or `rejected` |
| `registrations.checked_in_at` | Arrival time, or NULL |
| `registrations.admin_notes` | Private organizer notes, at most 2,000 characters; never returned to participants |
| `registrations.updated_at` | Last organizer change |
| `admin_audit_log` | Admin, action, target, JSON details, and time for every organizer change and CSV export |

## Payments, passes, and roles

`server/migrations/004_payments.sql` (idempotent) adds:

| Table / column | Purpose |
| --- | --- |
| `payments` | One row per registration (unique `registration_id`, cascade on delete) |
| `payments.amount` | Set by the server from `REGISTRATION_FEE` (default 1000) |
| `payments.transaction_id` | UPI reference, normalized to uppercase; unique across all squads |
| `payments.screenshot` / `screenshot_type` | Proof image as BYTEA (PNG, JPEG, or WebP, at most 5 MB, checked by magic bytes) |
| `payments.status` | `submitted`, `verified`, or `rejected`; a rejected row is replaced on resubmission |
| `payments.rejection_reason`, `reviewed_at`, `reviewed_by` | Review outcome shown to the squad and recorded for organizers |
| `registrations.pass_code` | 128-bit random hex code in the ID card QR (`HACKNEXUS:<code>`); set on verification, cleared on rejection |
| `registrations.checked_in_by` | Admin who scanned or marked the squad in |
| `admins.role` | `admin` (full access) or `scanner` (check-in only) |
| `admins.created_by` | Admin who added this account in the panel (NULL when added via the CLI) |

## Squad members

`server/migrations/005_members.sql` (idempotent) adds `registration_members`, primary key `(registration_id, position)`, cascading on registration delete:

| Column | Purpose |
| --- | --- |
| `position` | 1–4; position 1 is the squad lead, whose `email` always equals `registrations.lead_email` |
| `full_name` | 2–80 characters, whitespace collapsed |
| `email` | Lowercased; unique within the squad |
| `phone` | 10-digit Indian mobile number (`+91`/`0` prefixes and spacing are stripped); unique within the squad |
| `college` | 2–120 characters |

Members are optional in `POST /api/registrations` (the web form always sends them) but, when given, must cover exactly `squad_size` people. The registration and its members are inserted in one statement. The lead can replace them with `PUT /api/registrations/me/members` until the squad checks in. Admins see them in the squad dialog and in the CSV `members` column.

## API

| Method / route | Input | Result |
| --- | --- | --- |
| `POST /api/auth/signup` | `{ username, password }` | Creates a user and session |
| `POST /api/auth/login` | `{ username, password }` | Verifies credentials; creates a session. `user.mustSetPassword` is true for mobile-number and temporary passwords |
| `POST /api/auth/password` | `{ currentPassword, newPassword }` | Sets a chosen password; signs out the account's other sessions |
| `POST /api/auth/logout` | No fields | Deletes the current session and clears its cookie |
| `GET /api/auth/me` | Session cookie | Returns `{ user: { id, username } }` |
| `GET /api/registrations/me` | Session cookie | Returns only the current user's registration with its `members`, or null |
| `POST /api/registrations` | `{ teamName, email, domain?, squadSize, problemId?, abstract?, conductAccepted, members? }` | Persists a squad registration; `members` is `[{ fullName, email, phone, college }]` with the lead first |
| `PUT /api/registrations/me/members` | `{ members }` | Replaces the squad's member details (not after check-in); the lead's email is kept |
| `GET /api/health` | None | Checks database connectivity |

Admin routes require an admin session. Every change is written to `admin_audit_log`.

| Method / route | Input | Result |
| --- | --- | --- |
| `POST /api/admin/login` | `{ username, password }` | Verifies the admin password; creates an admin session (10 attempts per 15 minutes per IP) |
| `POST /api/admin/logout` | No fields | Ends the admin session |
| `GET /api/admin/me` | Admin cookie | Returns `{ admin: { id, username } }` |
| `GET /api/admin/stats` | Admin cookie | Totals, status/domain/challenge counts, registrations per day (IST, 14 days) |
| `GET /api/admin/registrations` | `q, status, domain (or none), checkedIn (yes/no), sort, page, limit` | Paginated registrations with usernames |
| `GET /api/admin/registrations.csv` | Same filters | CSV download |
| `GET /api/admin/registrations/:id` | Admin cookie | One registration |
| `PATCH /api/admin/registrations/:id` | `{ status?, notes?, checkedIn? }` | Updates review fields |
| `DELETE /api/admin/registrations/:id` | Admin cookie | Deletes a registration (the account remains) |
| `GET /api/admin/users` | `q, page, limit` | Accounts with admin flag, squad, and active session count |
| `POST /api/admin/users/:id/revoke-sessions` | Admin cookie | Signs a participant out everywhere |
| `DELETE /api/admin/users/:id` | Admin cookie | Deletes a participant account and its squad; admins are refused |
| `POST /api/admin/users/:id/reset-password` | Admin cookie | Issues a one-time temporary password (returned once, never logged) and signs the participant out; admins are refused |
| `GET /api/admin/audit` | Admin cookie | Latest 100 organizer actions |
| `GET /api/admin/payments` | `status, q, page, limit` | Payment submissions, awaiting ones first |
| `GET /api/admin/payments/:id/screenshot` | Admin cookie | The proof image, served inert (sandboxed, no-store) |
| `POST /api/admin/payments/:id/verify` | Admin cookie | Verifies payment, approves squad, issues pass (one statement) |
| `POST /api/admin/payments/:id/reject` | `{ reason }` | Rejects, revokes any pass, lets the squad resubmit |
| `POST /api/admin/attendance/scan` | `{ code }` (scanned or typed) | Checks the squad in once; `result` is `checked_in` or `already` |
| `GET /api/admin/attendance` | Admin cookie | Totals and recent check-ins |
| `GET/POST /api/admin/admins`, `DELETE /api/admin/admins/:id` | `{ username, password, role }` | List, add, or remove admins; you cannot remove yourself |

Check-in volunteers (`scanner` role) can call only `/me`, `/attendance`, and `/attendance/scan`; everything else returns 403.

Participant payment routes (participant session):

| Method / route | Input | Result |
| --- | --- | --- |
| `GET /api/payments/me` | Session cookie | Registration, payment status, fee, and UPI link/details |
| `POST /api/payments` | `{ transactionId, screenshot (data URL) }` | Submits proof (8 MB request limit on this route only; 10 per 15 minutes) |
| `GET /api/pass/me` | Session cookie | ID card details and QR payload once payment is verified |

All mutation requests must carry the configured `APP_ORIGIN`. Requests use parameterized SQL. Wrong passwords are limited to 10 per account per 15 minutes (a successful sign-in clears the count) and 100 per IP per 15 minutes; only failures count, so a shared campus network is not locked out. Account creation is limited to 50 per IP per 15 minutes; all API traffic is limited to 100 requests per minute per IP. These limits use an in-process store; shared limits are needed for a multi-instance deployment. Never cache `/api` responses at a proxy or CDN.

## Local data and production

The convenience runtime uses real PostgreSQL on loopback port **54329**, with data in `.local/postgres` and generated credentials in `.local/postgres.json` (file mode 0600). Both are excluded from Git. `Ctrl+C` stops the local server; data remains on disk. `npm run dev:local` reuses the same database on the next launch.

Production uses the `pg` connection pool and `DATABASE_URL`, independently of the local runtime. Set an HTTPS `APP_ORIGIN`, use TLS as required by your database provider, configure backups and a retention policy, and keep `.env` outside source control. `server/migrations/002_optional_domain.sql` upgrades existing databases without removing records. It drops the required-domain constraint, preserves challenge consistency, and adds normalized team uniqueness. It is safe to reapply. Existing duplicate names must be resolved by the organizer if they prevent creation of the new index; the migration never silently merges or deletes registrations.
